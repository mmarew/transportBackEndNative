1. Introduction

1.1 Purpose

This document specifies the system and architecture design of the Transport Management System Backend API v1.0.0 — the technical counterpart of the companion SRS. It is written so that an external reviewer can understand the architecture, the trust boundaries, the data flows and the design decisions without reading the source code, and so that a development team can maintain the system against a stable reference.

1.2 Scope

The system is a single deployable unit that serves the REST API, the Socket.IO gateway and static assets from one Node.js process, backed by MySQL and Redis, with outbound integrations to SMS, e-mail, push and payment services. Out of scope: the client applications and the internal workings of the third-party providers.

2. Architecture overview

2.1 Style

The system is a layered, service-oriented monolith: one Node.js process serves REST, WebSocket and static traffic. Strict layering — routes → middleware → controllers → services → CRUD/SQL — keeps business rules out of the HTTP surface, while cross-cutting utilities (validator, responder, error handler, logger, transaction context) are shared. Statelessness (JWT) plus the Socket.IO Redis adapter allow horizontal scale-out without code changes.

4. Component design

4.1 Layer contracts

  • Route — path constant (from Routes/EndPoints/*.js) + middleware chain (token → validator → guard) + controller. No business logic.
  • Controller — reads body/params/query and the authenticated user, invokes exactly one service, returns via ServerResponder.
  • Service — owns rules and state transitions; throws AppError on violations; wraps multi-statement work in the transaction executor; writes history records; triggers notifications.
  • CRUD — parameterized SQL helpers only; no business decisions.

4. Component design (continued)

4.4 The journey state machine

The behavioural core of the system. Statuses live in the JourneyStatus table (20 seeded rows); the id→name map and the class sets are defined once in Utils/ListOfSeedData.js and consumed by services, read paths and the reconciler. See the SRS §7 for the requirement-level rules; the design view is below.

4.5 Transition choreography (sequence)

Every transition follows the same five-step choreography; only the endpoint and the guard differ. Taking “driver starts journey” (8) as the example:

  1. Edge — client calls POST …/journeyStarted with the bearer token; VerifyToken resolves the user, the Joi validator checks the payload.
  2. Guard — the service loads the request row and its latest decision, verifies the caller's role/ownership and that the current status is in the allowed predecessor set (loaded = 7).
  3. Transaction — inside one DB transaction: update ShipperRequest.journeyStatusId, create the Journey record (or update its start timestamp + GPS), append a JourneyDecisions row, append history.
  4. Commit — the transaction commits; a non-throwing path returns the enriched request through ServerResponder (2xx envelope).
  5. Fan-out — post-commit: shipper gets the typed messages notification, driver's app receives the ack, any reconciler cache for the row is invalidated.
Design invariant

Clients never write journeyStatusId. Every status change is produced by a service action with a guard, inside a transaction, with a decision row and a history row — which is what makes reconciliation (FR-04.6) and the audit trail possible.

4.6 Read-path enrichment

The detail read service assembles each row with its decisions, linked driver, batch and assignment context. Active company-target rows without an exact-status decision keep their own status and attach the available decisions instead of projecting to waiting — the projection bug this rule prevents is exactly the “row shows no connected driver” class of defect. The list read applies connected-first ordering with an EXISTS(JourneyDecisions + DriverRequest) subquery so connected rows sort first without row multiplication.

5. Data architecture

  • 103 tables in domain groups: identity, transport core, companies/fleet, queue, bidding, finance, documents, delinquency, ratings, subscriptions, reference data — detailed in the TDD package (data-model.md).
  • Core chain: ShipperRequest → DriverBid / DriverRequest → JourneyDecisions → Journey → JourneyRoutePoints / DeliveryConfirmations, with status by journeyStatusId → JourneyStatus.
  • Keys: UUID business keys (*UniqueId, indexed) in routes and payloads; numeric surrogate ids for status maps and joins.
  • Audit: paired *History tables written through insertHistoryRecord; soft delete via *DeletedAt; append-only history.
  • Transactions: DatabaseTransaction + async-local context; the executor selection honours the ambient transaction, else the pool — so service composition stays transaction-safe.
  • Hot paths: paged reads on indexed sort keys; the connected-first ordering is a correlated EXISTS (no JOIN fan-out); Redis caches hot reads with TTL and is cache-through, not authoritative.
Reference data

Enumerations (journey statuses, roles, document types, payment statuses, cancellation reasons) are seeded rows joined on read and mirrored in ListOfSeedData.js so code and database stay aligned; tests assert the mirror.

6. API design

  • Surface: 204 routes / 285 operations in 27 groups; path constants centralised in Routes/EndPoints/*.js; the mount table lives in Routes/index.js (plus nested finance/company/queue/auth routers). The complete inventory with auth labels ships as endpoints.md.
  • Envelopes: success { message, ...data }; error { status:"fail", message, error:{ statusCode, status, isOperational } } with stacks dev-only.
  • Auth: Bearer <JWT>; 17 public operations (auth/registration, health, payment webhook, maintenance); jwtOrApiKey variant accepts x-api-key for E2E bootstrapping on DB endpoints.
  • Validation: Joi per route; pagination: page/limit/sortBy/sortOrder; limits: global + auth rate limiters; 1 MB body cap.
  • Versioning: asset version 1.0.0; unversioned paths tracked by release tags and this document set.
Maintenance endpoints (observed)

A handful of admin database-maintenance routes are reachable without a token (auth commented out in source) — e.g. POST /api/admin/createTable, DELETE /api/admin/dropTables. This is documented as observed; in production they must remain network-restricted at the edge. dropAllTables and the dev OTP viewer do require token/API-key.

7. Real-time architecture

client A ── socket.io ──▶ node-1 ──┐
client B ── socket.io ──▶ node-2 ──┼── Redis pub/sub (Upstash, TLS)
client C ── socket.io ──▶ node-1 ──┘        │
                                    room fan-out:
                                    queueOrg:<id>[:date]
                                    per-socket direct emits
  • Handshake: the client sends its JWT in socket.handshake.auth; init failures are answered with an error frame and the socket is disconnected.
  • Inbound events: queue:subscribe / queue:unsubscribe (room join/leave with ack), locationUpdateToDriver / locationUpdateToShipper (position relay + persistence), message keep-alive (acked with response).
  • Outbound events: queue board updates to rooms; typed notifications on the messages channel (78-kind catalog, default channel overrideable per call); location events including a replay of the last known position to newly connected sockets; structured error frames via sendError.
  • State: connection store per user (for socket lookup and fallback routing), last-location store; users without a live socket fall back to FCM push / polling.
  • Robustness: per-event try/catch → error frame (never crashes the loop); Redis adapter failures are logged and the process continues in single-server mode.

9. Error handling and observability

  • Uniform errors: services throw AppError(message, statusCode); the global handler renders the JSON envelope, logs 4xx as warnings and 5xx as errors with correlation (request id, method, path, user).
  • Logging: structured Winston logs — request logger (timing, status), validator failures with field details, socket errors with stacks, application API errors. Client mistakes and server faults are logged in distinct classes so E2E results correlate to backend logs.
  • Health: GET /api/health (liveness) and GET /api/health/database (DB reachability) — public, polled by monitoring; admin DB-stats endpoint for operators.
  • Performance: query-performance middleware captures slow queries; request ids tie client reports to logs.

11. Testing strategy

  • Unit/integration (jest): 102 tests over services and utilities (status logic, validators, helpers).
  • End-to-end: a 248-check suite covering registration → login → OTP → request lifecycle → bidding → assignment → journey → cancellation, plus negative probes (401/400/404) and a socket harness (room subscribe, board broadcast, location relay, typed messages).
  • Route contract checks: the published endpoint inventory is verified against a running instance by live preflight probes — only routes that answer non-404 are listed, auth labels come from observed 401 behaviour.
  • Regression gate: per-run baselines with named failure comparison (e.g. 239 passed / 3 known-failing / 6 skipped) so new breakage is distinguished from accepted debt.
