1. Introduction

1.1 Purpose

This document specifies the requirements for the Transport Management System Backend API (the “system”), the server-side component of a freight/transport management platform. It is the API Requirements Documentation (SRS) for the asset transport version 1.0.0 submitted for asset registration, and it is written for external review as well as for the project's own development and test baseline.

1.2 Scope

The system provides the complete server-side functionality of the platform:

  • Identity: registration, contact verification by one-time password (OTP), authentication (JWT) and role-based authorization for 12 platform roles.
  • Transport demand: shipper requests with a 20-state journey lifecycle, driver bidding, company-target batch dispatch, assignment and replacement workflows.
  • Journey execution: loading stages, GPS route tracking, proof of delivery and delivery confirmation with photo evidence.
  • Supply: company registration and approval, memberships and roles, fleet and driver–vehicle assignment, a FIFO dispatch queue for queue organizations.
  • Real-time features: location exchange between driver and shipper, queue boards, typed in-app notifications over Socket.IO.
  • Finance: deposits completed by payment-gateway webhook, balances, commissions, refunds and tariff rates.
  • Supporting functions: document/media management, SMS/e-mail/FCM notifications, ratings, delinquency governance, subscriptions, administration and health endpoints.

Out of scope: the web and mobile client applications (separate systems that consume this API) and the external payment, SMS, e-mail and push providers themselves. All business records of account — journey state, permissions, financial entries — are held by this system; clients hold no business logic of record.

2. Overall description

2.1 Product perspective

The system is a self-contained backend service executed under PM2 behind an Nginx TLS terminator. It persists data in MySQL (103 tables), uses Redis for caching and for scaling Socket.IO across nodes, and integrates outboundly with SMS, e-mail, push and payment services. It is the single authority for all business state of the platform: clients render, the server decides.

2.2 User classes and actors

ActorRole idPrimary capabilities through the API
Shipper1Create/cancel transport requests, select bids, confirm delivery, manage documents, deposits.
Driver2Receive offers, bid/accept/reject, drive loading stages, report location, queue check-in, view earnings.
Admin / super admin3 / 6User and role governance, force status changes, delinquency decisions, system maintenance, analytics.
Vehicle owner4Register vehicles, assign drivers, maintain vehicle documents.
Company admin / staff / dispatcher7 / 8 / 10Company profile, memberships and roles, fleet, bids, assignments, dispatch.
Queue org admin / dispatcher11 / 12Operate the dispatch queue: orders, driver check-in/out, FIFO offers, audit trail.
Payment provider—Delivers signed webhooks for deposit completion (public endpoint).
Monitoring system—Polls health endpoints (public).

2.3 Operating environment

  • Runtime: Node.js ≥ 20, Express 5, PM2 process manager, Linux server (production).
  • Data stores: MySQL 8 (primary), Redis/Upstash over TLS (cache + Socket.IO adapter).
  • Clients: browser SPA and React Native mobile app over HTTPS and WSS.
  • Environments: production (app.dynamicsroute.tech), staging (dev.dynamicsroute.tech), local development.

2.4 Constraints

  • All traffic over TLS; JSON bodies (1 MB limit), multipart only for uploads.
  • JWT lifetime fixed at 24 hours; no refresh-token endpoint in v1.0.0.
  • Personal data (names, phones, e-mail, GPS traces) processed under access control; production error responses must never expose stack traces.
  • Status transitions and financial postings must be transactional and audited.

2.5 Assumptions and dependencies

  • Clients enforce UI validation; the server remains the authority for all rules.
  • SMS/e-mail delivery is provided by configured providers; outside production the test OTP 101010 is used.
  • MySQL, Redis, SMTP, SMS, FCM and the payment gateway are external availability dependencies; the design degrades gracefully (see NFR-04).

4. External interface requirements

4.1 REST API — IR-01

  • Volume: 204 distinct routes / 285 operations in 27 groups (/api/user, /api/company, /api/finance, /api/queue…, /api/admin, /api/vehicle, plus root-mounted utility routes). The full table with an auth column per route ships as endpoints.md in the Request/Response package.
  • Protocol: HTTPS, JSON bodies (UTF-8); multipart/form-data for uploads; production base https://app.dynamicsroute.tech.
  • Authentication: Authorization: Bearer <JWT>. 17 operations are public: registration/verification/login/OTP/logout, two health endpoints, the SantimPay webhook, and a small set of maintenance endpoints (database stats, cache clear, create/drop-table helpers, role-status helper).
  • Success envelope: HTTP 2xx with at least a message field plus resource data.
  • Error envelope: { status:"fail", message, error:{ statusCode, status, isOperational } } for 400/401/403/404/409/429/5xx; stack traces only in development.
  • Pagination and sorting: page, limit, sortBy, sortOrder.
  • Validation: Joi schemas per route — all violations reported at once, unknown fields stripped, empty POST body rejected with 400.
  • Rate limits: a global limiter plus a stricter limiter on /api/user auth routes; 429 when exceeded.

4.2 WebSocket — IR-02

  • Socket.IO over /socket.io (websocket and polling transports, Engine.IO v3 compatible), JWT supplied in the handshake auth, CORS allow-list, optional Redis adapter for multi-node fan-out.
  • Client→server: queue:subscribe, queue:unsubscribe, locationUpdateToDriver, locationUpdateToShipper, message.
  • Server→client: queue board events, queue:subscribed/unsubscribed acks, messages typed notifications (78 kinds), location events (with replay of last position), response acks, structured error frames.
  • Rooms: queueOrg:<id> and queueOrg:<id>:<date>.

4.3 File interface — IR-03

  • Upload: multipart with size limits; images re-encoded; document type and duplicate checks before persistence.
  • Serving: static /uploads and /Assets behind access rules.

5. Data requirements

  • 103 MySQL tables grouped as: identity (users, credentials, roles, OTP, devices), transport core (requests, batches, driver requests/bids, journeys, decisions, statuses, route points, cancellations, POD), companies and fleet, dispatch queue, bidding/assignment, finance (deposits, balances, commissions, tariffs), documents, delinquency/governance, ratings, subscriptions and reference data. The full list with relations is in the TDD package (data-model.md).
  • Keys: UUID business keys (*UniqueId) used in routes and payloads; numeric surrogate ids for status maps and legacy joins.
  • Audit: paired *History tables record every mutation with actor and timestamp; status history and a queue audit log are first-class.
  • Retention: soft delete (*DeletedAt) on business entities; history rows are append-only.
  • Integrity: parameterized SQL only; multi-step writes execute in database transactions; reference values (statuses, roles, document types) are seeded rows joined on read.
Sensitive-data inventory

Personal data held: names, phone numbers, e-mail addresses (users and receivers), GPS traces (JourneyRoutePoints, last-location store), document images (IDs, licences), financial records (deposits, balances). All are access-controlled by bearer authentication plus role/ownership scoping; none appear in production error responses or logs at info level.

7. Business rules and journey state model

Every transport request moves through a 20-state machine held in the JourneyStatus table and enforced by server-side services. Clients never write the status; they call action endpoints (offer, accept, reject, select, loading-stage, cancel, confirm-delivery) and the server derives the next state transactionally.

7.1 Status classes (business rules)

ClassStatus idsRule
Active2, 3, 4, 5, 6, 7, 8Live requests; the only statuses automatic reconciliation may rewrite; driver connection and enrichment apply.
Supporting (decision-backed)2–9A positive decision still evidences a live/completed request; list output attaches the connected driver and decisions for these rows (connected-first ordering).
Terminal10, 12, 13, 14, 15Deliberate end states; never re-opened, never reconciled — rewriting one to waiting would resurrect a cancelled order.
Pre-connection1waiting: created but no driver connected; rendered as an inactive order until a decision appears.
Completed9Terminal but decision-backed; still receives journey/POD enrichment on read.
Batch20partiallyCancelled: applies to batches; per-slot rows keep their own terminal statuses.

7.2 Key business rules

  1. Offers expire without an answer → status 16 and automatic re-offer to the next driver.
  2. A bid can be accepted only once the driver's acceptance (3) precedes shipper selection (4); losing bids become 17 or 11.
  3. Loading-stage transitions (5→6→7→8) require the selecting decision and stamp time + GPS.
  4. Cancellation reason lists and allowed actors differ by context (individual vs company) and role (shipper 1, driver 2, admin 3, queue org admin 11).
  5. Company assignment may replace an individual driver link → status 19 on the replaced link.
  6. Batch partial cancellation (20) never rewrites completed or in-transit slots.
  7. Only statuses inside the active set may be corrected by reconciliation; all corrections write a decision/history row.
